# 当前开发进度与下一步产品方向

评估日期：2026-10-07。性质：依据现有实现、原始开发计划和网络资料形成的方向建议，不是已实施功能、正式架构冻结或新增生产部署授权。本轮仅整理文档，不恢复受阻的 Docker/GitHub 操作。

## 一、当前定位

当前是具备普通题、特殊判题、交互题及固定双角色通信题的本地教学原型。功能探索已超过最初“显示题面并检查 C++ 编译”的 MVP，但持久业务和当前真实运行验收尚未完整，不能称为完整生产 OJ 或已完成原计划 Phase 8。

## 二、与原计划的对应关系

Phase 0 基础已完成；Phase 1/2 的部分可见功能已有增量实现，Phase 4/5/7/8 的若干题型与执行能力提前探索。Phase 2 的数据库提交记录与身份授权、Phase 3 的异步队列/恢复，仍是产品化缺口；Phase 6 比赛榜单、Phase 9 集群、Phase 10 生产运维未形成交付。

因此下一步应补齐“稳定运行 → 持久提交 → 可恢复判题”的主线，再扩展特色。原文档对长期执行图、聚合资源和多语言的设想属于后续设计输入，不因原文中的命令式表达而自动授权实施。

文档治理也需收束：部分早期架构文件仍写“只有骨架”，通信契约开头还保留旧完整检查失败状态。实时结果以 PROGRESS 最新段为准；后续应增加“当前实现拓扑/目标拓扑”对照和版本说明，避免后续 Agent 从历史段落误判。此次评估不顺手改写核心契约或抹去历史证据。

## 三、网络资料带来的判断

调研采用项目官方文档与原始研究，访问日期均为 2026-10-07。功能对比不是完整市场调查，没有据此声称全球首创。

| 资料                                                                                   | 可核实事实                                                           | 对本项目的启示                                                                                       |
| -------------------------------------------------------------------------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| [CMS Task types](https://cms.readthedocs.io/en/latest/Task%20types.html)               | 已有 Batch、Communication、Interactive 等模型以及 checker/score 区分 | “支持通信题/特判”本身不是独特卖点。CMS 的 manager/选手结构与本项目两份选手源码不同，不能宣称直接兼容 |
| [DOMjudge Judging](https://www.domjudge.org/docs/manual/8.2/judging.html)              | 重判保存旧判断，并可先检查一批新结果，再采用或取消                   | 提交历史、版本与可审阅重判属于实用基础，优先于扩集群                                                 |
| [testlib 官方 README](https://github.com/MikeMirzayanov/testlib/blob/master/README.md) | 提供 checker、interactor、validator、generator 范例                  | 教师出题工具应借鉴已有格式，重点降低制作和验证成本；不能把成熟工具能力包装成首创                     |
| [CodeAid，CHI 2024](https://arxiv.org/abs/2401.11314)                                  | 在 700 人编程课程、12 周部署中研究不直接给答案的支持方式             | 分级提示和透明控制值得试验；部署研究不能直接证明长期学习增益                                         |
| [ClassAid，2026-02 预印本](https://arxiv.org/abs/2602.06734)                           | 研究教师动态控制 AI 帮助模式和课堂交互视图，含 54 名学生课堂反馈     | AI 应受教师教学目标控制；不是接聊天框即可形成优势，也不能把小规模研究当普遍有效证明                  |
| [师生需求研究，2026-03 预印本](https://arxiv.org/abs/2603.22673)                       | 50 名教师与 90 名学生的调查呈现间接引导和直接帮助之间的偏好差异      | 教师可配置提示程度、学生知道提示边界，比默认给完整代码更符合双方需求                                 |

以下定位是从资料和本项目基础推导出的产品假设：**面向算法与系统思维教学，以可解释的交互/通信实验和教师出题质检为特色的 OJ。** 先验证这一细分方向，暂不同时追求通用竞赛平台、云编译平台和全能 AI 导师。

## 四、优先验证的三个创新方向

### 1. 可视化通信实验室：主打方向

围绕现有双编辑器，提供公开训练数据上的通信事件回放、累计字节预算、退出/EOF/超限位置和两个解法的协议对比。教师可把一个练习拆成“先跑通、解释发生了什么、减少通信开销”三个步骤。

最小范围只处理现有固定单向图，不先做任意多进程。记录有界原始字节事件及观察顺序；底层一次 read 的分块不是协议消息，只有明确分帧的协议才展示消息数。回放是已记录事件的查看，不承诺确定性重现操作系统调度。

学生仅在自己输入或教师明确公开的数据上查看训练回放；隐藏评测继续只给摘要，教师/工程师按服务器策略取得允许的明细。不能为了“可解释”泄露隐藏测试或工程内部信息。增加事件捕获、存储和投影属于新接口，须先受审并度量开销。

A+B 适合环境检查和入门，不足以证明有通信算法训练价值：现在无法静态确保求和一定由接收端完成。后续真正的信息约束练习可设计为双方各持私有输入，例如一方持数组、另一方持查询；这需要新增输入视图契约并独立验证，当前不能直接上传后假称支持。

验证方法：先请少量教师/学生使用公开任务比较普通日志与回放，记录定位协议错误耗时、能否解释 EOF/超限、完成新题的表现。界面看起来丰富、一次 AC 或通信量下降都不能独立证明学习效果。

### 2. 教师题目质检工作台：最先落地的特色功能

把“上传即可发布”完善为“草稿 → 数据检查 → 标准解/典型错解回归 → 三模式预览 → 确认发布”。检查重复数据、输入范围、答案/特判一致性、各组边界覆盖和已登记错解是否被识别。

第一版只要求数据、参考解和一组带预期结果的错解；先用现有受限 judge 执行，不立即接收任意生成器。之后再按沙箱边界接入 validator/generator 与 testlib 适配；参数顺序、退出码和评分格式需显式转换，不能把外部 checker 直接当现有协议执行。

前端新增教师草稿向导、文件配对预览、质检报告及学生视角预览；后端保存题目版本、测试方案、回归结果和发布状态。学生仍保持简洁题面/编辑器/结果。验收使用固定的坏题包，要求预先指定的非法输入、错误答案和不一致 checker 都能被标出；“登记错解拦截率”仅反映该错解集，不称为完整测试覆盖率。

这能复用已有教师上传、特殊判题和通信双模板，改造范围比通用执行图小。创新价值在于三种题型统一的教师工作流、易懂报告和可追溯发布；是否降低备课成本必须通过教师试用验证。

### 3. 教师可控的分级提示：后续试验

提示分为概念提醒、定位思路、伪代码三档，教师按练习决定开启程度；考试可关闭。首版可先使用教师编写的提示和规则映射，再评估引入 LLM，不必从开放聊天开始。

生成提示时只提供经授权的学生源码、公开题面与允许的诊断；隐藏数据和答案不进入学生可见提示链。最终 verdict 仍由确定的编译、运行及 checker 产生，AI 不改变成绩。教师可审阅、撤销提示，系统记录采用的提示策略版本。

主要验证指标为后续无提示新题表现、错误提示率、教师修订负担和答案泄露检查，而不只看当前题 AC 率。上述研究为设计提供依据，不能预先保证本项目引入 AI 后有效。完成持久提交和身份/课程边界后再实施真实课堂版本。

## 五、建议执行顺序与验收门槛

| 顺序 | 交付单元                 | 对应原计划                             | 可检验完成条件                                                                                                            |
| ---- | ------------------------ | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| A    | 稳定、可交付的当前 MVP   | Phase 1/4 与已有增量收尾               | 正常授权 Linux 环境、当前镜像/源码绑定；通信 12 项矩阵及取消/EOF/清理；旧题型回归、上传重启、三模式页面；远程源码实际交付 |
| B    | 提交记录、版本和重判历史 | Phase 2 为主                           | 双源码和首次 JudgeRun 原子保存；刷新/重启仍可查；每次重判新增 Run；题目/数据/工具版本可追溯                               |
| C    | 小规模可恢复判题         | Phase 3；多人试用前补 Phase 2 身份授权 | 任务状态、忙/队列/取消明确；Worker 失败可恢复、不重复写终态；服务端真实权限不能由模式按钮提升                             |
| D    | 教师质检 + 公开通信回放  | Phase 5/7/8 的受控增量                 | 一套题目发布质检工作流、几道有教学梯度的公开通信实验、隐藏数据边界检查及教师试用报告                                      |
| E    | 可控提示试验             | 教学产品增量                           | 教师开关与审阅、提示版本、允许输入边界、无提示迁移任务评估；收益不足则不扩大投入                                          |

环境未恢复时可先完成 B 的 schema/事务设计、D 的页面原型和教学脚本、试用访谈提纲；这不等于已通过 A。新的业务/执行契约须按原流程先审后实现。Linux 运行环境应通过正常授权配置，Windows 保留开发编辑；不以更换通道绕过当前审批。

真实账号之前维持当前“本机手动模式”的产品约定。准备邀请多名真实学生或对外访问时，身份与服务端权限成为前置；这是下一阶段提案，不把用户此前选择的无登录演示擅自改掉。

暂缓 K8s、多节点调度、全语言支持、大规模榜单和任意图执行；这些需要稳定负载或课程需求支持。先用受控试用采集并发与排队数据，再决定容量目标，不预设无法验证的高并发数字。

## 六、下一轮具体分工建议

Architect：把已有 MVP 与长期目标拓扑对齐，先设计 Submission/SourceUnit/JudgeRun 事务、版本和权限边界，再审 trace/评分扩展。Builder-Backend：按受审模型实现持久记录、查询/重判和恢复；Builder-Frontend：提交列表/详情、教师质检向导、公开回放组件；Worker：数据包、正确/错误协议例题、页面状态和文档；独立 reviewer：检查故障恢复、隐藏数据边界、当前真实证据与版本绑定。

本轮没有派发这些实施任务。建议下一次开发明确以“当前真实验收 + 持久提交闭环”为主目标，特色功能先做教师质检和公开通信回放的小范围验证，再决定 AI 投入。
