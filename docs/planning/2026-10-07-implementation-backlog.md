## 4. NEXT-001：先冻结持久模型和 API

输出一份可审 ADR、ER 图、状态迁移表、请求/响应 fixture 和迁移方案。以下是提案，需要审阅后实现：

- `Submission`：ID、题目版本、创建者/演示主体、语言配置版本、创建时间、幂等键、源集合摘要。不得把 X-OJ-Mode 保存为可信用户身份。
- `SourceUnit`：submission_id、role、原始 UTF-8 字节和摘要；`(submission_id, role)` 唯一。单源码与 sender/receiver 完整集合一次事务写入；缺角色整笔失败。角色与产物显式绑定。
- `JudgeRun`：ID、submission_id、原因（首次/重判）、状态、判定、源/题目/数据/checker/compiler/runtime 版本和摘要、时间、错误分类。每次重判新建 Run；保留旧结果。
- `CaseResult` / 角色产物与诊断：按 Run 归属、大小上限和权限保存；学生 DTO 不含隐藏 input/expected/stdout/transcript。CPU/内存未知用 null，不填估算零值。
- 题目版本与数据对象：明确内容寻址、不可变清单、发布指针和保留策略。只存 hash 没有原字节不能重放历史；源码、数据、checker、工具镜像必须可取回或明确标记历史无法重判。
- 建表前核对现有空 schema、迁移工具、pgx/sqlc 的已有依赖，确定版本与可重复迁移流程；不同时引入第二套 ORM。旧文件题库保留，用可重复导入建立首版引用，不搬走原数据。

API 提案：`POST /api/v1/submissions`、`GET /api/v1/submissions`（游标分页）、`GET /api/v1/submissions/{id}`、`GET /api/v1/judge-runs/{id}`、`POST /api/v1/submissions/{id}/rejudges`。定义 400/404/409/413/429/503 和关联 request_id；幂等键相同且内容相同返回同次提交，内容不同返回冲突。

Phase 2 可暂保留同步 worker HTTP：短事务保存完整 Submission/SourceUnits/首次 Run，提交后调用独立 worker，再用短事务提交结果；不能持有数据库事务等待编译。客户端断线后已保存的提交可通过幂等键/历史查询找回，重试不得重复执行。无异步恢复前，启动时将确认已中断的运行标为基础设施失败并允许新 Run 重判；不能宣称自动恢复执行。Phase 3 再改为事务 outbox + 202 排队接口，接口版本和兼容策略一并审阅。

验收：设计覆盖提交事务失败、重复请求、角色顺序不同、断线/重启、题目更新、重判并发、无权限查询、数据保留和删除。独立审阅通过后才生成正式 schema/实现任务；当前未冻结。

## 5. NEXT-002：后端持久闭环

执行步骤：受审 migration → repository 事务 → 业务服务 → API 白名单 DTO → worker 结果落库 → 受控恢复/历史查询。API 仍不拥有执行源码或控制 Docker 的能力。

必须通过的测试：

1. 双源码事务中第二份写入失败，Submission/SourceUnit/Run 均不留下半成品；正常提交保存字节及正确摘要。
2. 同一幂等请求并发到达只创建一个 Submission/首次 Run；响应丢失后可安全找回。
3. 结果落库失败不能显示完成；相同结果重送不能重复写入，冲突结果不能覆盖终态。
4. 修改当前题面/数据后历史提交仍展示当时版本；重判按所选版本新建 Run，并明确默认使用历史版本还是最新版本。
5. 重启仍能查询历史；中断运行有确定处置；旧记录/已有教师目录和卷不丢失。
6. 分页稳定、有最大页长；非法 ID、越权、学生请求扩展隐藏字段均失败或只返回白名单。

交付数据库迁移日志、API 示例、实际集成报告；mock 通过不能替代 PostgreSQL 事务验证。只读故障诊断不修改用户原题库。

## 7. NEXT-004：异步判题和失败恢复

先设计再实现：保存提交/Run/outbox 同一事务，dispatcher 发布 Redis Streams，worker 获取具有租约及 fencing token 的 attempt。业务 rejudge 新 Run，传输重试新 attempt，二者不混用。

任务验收按故障窗口逐项注入：数据库提交前失败、outbox 发布前/后崩溃、worker 领取后失联、结果提交后 ACK 前崩溃、租约过期后旧 worker 迟到、重复消息、取消和完成竞态。DB 终态事务成功后才 ACK；过期 attempt 无权写结果；清理不明的节点不恢复接单。不要用“消息只投一次”的假设替代幂等。

前端才在此阶段启用 queued/running/finished 的正式异步状态。队列/每人并发/节点容量有硬上限，拒绝请求不创建无限排队记录；轮询和 SSE 二选一先完成简单可靠方案。

## 8. NEXT-005：教师题目质检工作台

后端工作流：草稿 → 结构验证 → 固定参考解和登记错解回归 → 三模式预览 → 发布不可变版本。失败留在草稿；审核任务自身受 SEC-005 预算约束。参考解、错解和上传 checker 都按不可信源码编译/执行。

前端沿用 UploadPage，拆为 `ProblemDraftWizard`、`DataPairTable`、`CheckerSelector`、`ReferenceSolutionEditor`、`QualityReport`、`PublishPreview`。步骤为题型/题面、数据配对、判题规则、参考解/错解、预览发布；可以后退且不丢草稿。错误定位到具体字段或文件；学生预览使用公开 DTO，不能读取完整数据后仅折叠。

标准题检查输入/答案配对；构造题用多种合法输出 AC 和违反约束输出 WA 验证规则；通信题分别提供 sender/receiver 模板、字节上限及 EOF 说明；交互题先限现有固定协议。首版不接任意 generator、在线下载包或任意编译参数。

验收包必须包括正常题、缺文件、越界输入、重复数据、错误标准答案、始终 AC 的错误 checker、checker 超限、典型错解漏检、发布中断。报告区分阻断错误和提示；只能声称识别了登记错解，不称证明题目无漏洞。记录教师完成一次发布所用步骤/时间和修正负担，再决定扩大功能。

## 9. NEXT-006：公开通信实验与回放

只对教师明确标记公开的实验输入开放 trace；隐藏评测仍只给学生汇总结果。新 DTO 必须来自单独公开实验执行路径，不能把隐藏 Run 结果加一个前端开关后开放。

`CommunicationReplayPage`：sender/receiver 源码卡片、字节进度、方向、EOF、退出状态、截断标记和事件时间线。事件协议区分 observed/accepted/closed；写入中继成功不等于对端程序已读取。系统读取块不是一条逻辑消息；没有协议 framing 就显示字节片段，不能伪造消息边界或精确消费时间。

第一组教学场景：正确 A+B、缺 flush/不结束、超过通信预算、接收方提前退出、负数/大数。错误程序只在受限 worker 中运行。A+B 无法证明一定由接收方求和，双端均由同一提交者控制；真正的信息约束题需要新增双方私有输入视图，另立契约。

验收：同一公开 trace 可重复呈现，说明它是观察记录而非操作系统确定性重演；隐藏数据不能通过 ID、更换模式参数、旧缓存或下载接口流出；长文本/二进制/控制字符有界并安全显示。用学生能否解释通信失败和修改次数评估价值。

## 10. 交付和恢复标准

每个工作包保存设计版本、改动清单、实际命令/环境/退出码、失败与未执行项、独立审阅和交接。需要核心契约变更时先评审再实现；不以 task done 替代产品验收。

Docker/GitHub 的处理继续沿用[审批与引擎档案](../issues/2026-10-07-approval-diagnosis-and-recovery.md)和[上传档案](../issues/2026-10-07-github-write-access.md)。10-08用户要求推送后已正常重试GitHub：获准沙箱外Git查询仍connection reset，连接器写入仍403，未产生远程提交/分支/PR；本轮未重试Docker。连接恢复后按正常授权路径复验，失败记录一事一档。安全事件或清理不确定时停止受影响执行池，不靠重启掩盖残留证据。
